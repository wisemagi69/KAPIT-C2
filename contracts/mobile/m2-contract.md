Mobile protected routes accept only `Authorization: Bearer <access_token>`; a browser session alone cannot authenticate them. Public mobile auth adapters have an empty authenticator list and validate their explicit credential, so a cookie cannot alter their meaning. Other mobile roles cannot enroll or retrieve source through this slice. Mobile tokens do not authenticate existing web/review/admin/recipient routes. Keep DRF's global SessionAuthentication and web CSRF rules unchanged. This is bearer authentication, not DPoP, mutual TLS, MFA or hardware attestation.

Unknown request fields and duplicate query parameters fail; never reflect unknown field names or supplied values. Query strings are forbidden except on the bounded report list. The device list takes no filters and returns at most 100 entries; new enrollment is denied at 20 active enrollments or 100 lifetime enrollments for one user, so no inaccessible tail is silently truncated. This bounded synthetic-demo cap includes revoked historical identities; there is no automatic deletion or reactivation.

## Enrollment and proof objects

ChallengeRequest contains exactly:

```json
{"username":"synthetic.submitter","password":"<entered at runtime>","installation_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","enrollment_id":null,"public_key_spki":"<base64url DER SPKI>","label":"Synthetic test phone"}
```

`username` and `password` follow existing LoginSerializer bounds (150/128 characters, no trimming). `installation_id` is a canonical lowercase UUID generated once for this installation. `enrollment_id` is null for NEW_ENROLLMENT or a canonical UUID for REAUTHENTICATE. It is a lookup hint, not identity authority. `label` is 1–80 Unicode scalar values, not blank after whitespace inspection, with no control characters; display it as escaped text. It is user-supplied metadata, never hardware identity. `public_key_spki` is at most 200 base64url characters, strictly unpadded canonical encoding of X.509 SubjectPublicKeyInfo DER for an EC secp256r1/P-256 public key only. Reject another curve/key type, trailing DER data and noncanonical re-encoding. Fingerprint is lowercase SHA-256 hex of those exact validated SPKI bytes.

After password verification, lock and recheck active organization/user, submitter role and exactly one current eligible unit/channel. The server binds challenge to authenticated user, organization, permission_version, current password/session-auth stamp, installation UUID, fingerprint, normalized validated public key, requested action and enrollment (or null), server expiry and random nonce. It stores the nonce digest plus the immutable binding, not password. It may replace outstanding challenges for the same binding. ChallengeResponse:

```json
{"protocol":"kapit-mobile-v1","challenge_id":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","action":"NEW_ENROLLMENT","user_id":"cccccccc-cccc-4ccc-8ccc-cccccccccccc","organization_id":"dddddddd-dddd-4ddd-8ddd-dddddddddddd","enrollment_id":null,"installation_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","key_fingerprint":"<64 lowercase hex>","nonce":"<43 base64url characters>","server_time":"2026-10-17T04:00:00.000000Z","expires_at":"2026-10-17T04:02:00.000000Z","proof_message":"<exact UTF-8 text specified below>"}
```

Auth abuse bounds are fixed for this contract: every challenge/token/refresh call consumes a shared pre-auth socket-peer bucket of 30 attempts per fixed 300-second window; challenge also consumes a keyed-digest-of-exact-username bucket of 10 attempts per 300 seconds before account lookup/password hashing. Ignore forwarded-IP headers on this loopback-only service. Successful challenge issuance is additionally limited to 5 per user per 300 seconds and at most 3 outstanding challenges per user; issuing a fourth atomically consumes the oldest. Both valid and invalid requests consume their relevant attempt budget, so 429 reveals no account-existence result. Return `THROTTLED` with integer Retry-After until window end, without input values. Check bounded JSON/key/label sizes before expensive password or curve operations. Store atomic counters in a dedicated bounded database throttle table (4096 maximum keys), keyed using server-secret HMAC rather than plaintext usernames/IPs; expired counter rows older than 24 hours may be replaced inline in bounded batches of100 because these are ephemeral security counters, not source/receipt retention. If counter capacity or storage is unavailable, fail auth closed with safe503; never silently disable limits. Counter transactions finish before identity locks to avoid lock inversion. Challenge rows remain bounded to3 unconsumed per user, contain only bounded bindings and nonce digests, and may be discarded after24hours once consumed/expired; immutable acceptance records are untouched. Tests use these exact bounds with controlled time/isolated counters, not a production-wide throttle bypass.

The signed text is the following ten LF-separated ASCII content lines, with a final LF. UUIDs are canonical lowercase; null enrollment is literal `-`; expiry is an integer Unix UTC second (not the timestamp spelling). No CR, spaces, BOM or trimming. The response supplies `proof_message`, and the app reconstructs and checks it from all returned fields before signing:

```text
KAPIT-C2-MOBILE-PROOF-V1
NEW_ENROLLMENT
bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb
cccccccc-cccc-4ccc-8ccc-cccccccccccc
dddddddd-dddd-4ddd-8ddd-dddddddddddd
-
aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa
<64 lowercase hex fingerprint>
<43 character nonce>
<integer challenge expiry>
```

There are **ten content lines and one trailing LF**, not an extra blank-line field. `REAUTHENTICATE` replaces the action and uses the existing enrollment UUID. Sign exact UTF-8 bytes using Android `SHA256withECDSA` with the installation's Keystore P-256 private key; output DER ASN.1 ECDSA signature encoded canonical base64url without padding (at most 100 characters). Server verification uses maintained `cryptography` ECDSA/SHA-256 primitives, not handwritten ECDSA. Server accepts either valid ECDSA s representation; challenge consumption, not signature uniqueness, prevents replay. Android's proof key is separate from its AES wrapping key. It may be usable without per-signature biometric authentication because proof only runs inside explicit online credential entry; it cannot unlock the report database or renew offline access by itself. TASK-057 verified P-256 Keystore signing on the owned API36 emulator and Python/Kotlin DER interoperability; physical-device behavior remains TASK-075.

TokenRequest is exactly `{challenge_id, nonce, signature}`. Server reconstructs signed bytes from stored binding and supplied nonce; constant-time compares nonce digest, validates expiry/proof and rechecks current password/permission/scope under locks. The challenge is consumed atomically before issuing one family. Invalid proof consumes that challenge as well; denial consumption must commit even when the response is 401. All expired/used/unknown/invalid challenge failures share `AUTH_REQUIRED`, revealing no enrollment or key. Challenge responses identify an account only after successful password authentication.

NEW_ENROLLMENT: create a stable server-issued enrollment UUID bound permanently to user/org/key/installation. Key fingerprint is globally unique across active and revoked enrollments, and owner+installation UUID is unique. Android therefore uses a separate P-256 proof alias per account/enrollment, not one device-global key; account B never uses account A's proof key. The same key cannot enroll another owner or another installation. Return `ENROLLMENT_EXISTS` after valid password+proof for the owner's active binding and require explicit REAUTHENTICATE with its returned enrollment UUID; a revoked owner binding returns `ENROLLMENT_REVOKED` and never reactivates. A key already bound to another owner returns generic `ACCESS_DENIED` without its identity. The enrollment-exists error may include `enrollment_id` only when owner, key and installation all match after password+proof. A new key plus new installation may enroll after valid current credentials; it cannot adopt an old namespace/queue and does not prove a different physical phone. Changing installation UUID while retaining a revoked key cannot bypass revocation; unmatched key/installation combinations return generic `ACCESS_DENIED`.

REAUTHENTICATE: stored user/org/fingerprint/installation and supplied enrollment must all match and be active. Revoke this enrollment's existing families and create a fresh family; keep enrollment and operation namespace unchanged. Other enrollments and current browser sessions remain unchanged. A lost token-issuance response is recovered by a fresh password challenge with the same key: an existing enrollment is discovered only after proof, then resumed; do not create duplicate enrollments or silently assign an old queue to a different binding.

## Session objects, rotation and current authority

SessionResponse contains exactly `token_type` (`Bearer`), `access_token`, `access_expires_at`, `refresh_token`, `refresh_expires_at`, `context`. `context` is ContextResponse below. Dates are UTC RFC3339 with `Z` and six fractional digits in auth responses; report response dates preserve existing M1 serializers. Client never hashes an auth-response timestamp. Refresh credential format is `<canonical credential UUID>.<43-character base64url secret>`; secret is 32 CSPRNG bytes. Persist only SHA-256 of the complete credential and rotation metadata server-side; compare in constant time. Credential UUID is only a lookup handle. Tokens remain in protected enrollment-owned client storage and are excluded from backup.

JWT header fixes `alg=HS256,typ=JWT`; no header URL/jwk is accepted. Claims are `iss`, `aud` (single string), `sub` (user UUID), `org` (organization UUID), `did` (enrollment UUID), `sid` (family UUID), `pv` (integer permission version), `role` (`submitter`), `iat`, `nbf`, `exp` (integer seconds), `jti` (random UUID), `token_type` (`access`). Require all claims, strict types and exact issuer/audience/algorithm/type. `nbf=iat`; `exp=min(iat+600,family_expiry)`. Require family expiry strictly in the future, and reject future-issued or zero-duration tokens. Tokens disclose only scoped identity metadata and confer no authority without live database checks.

Before any protected read/write, lock organization then user then enrollment then family; compare all token identity/role/permission claims against persisted state and compare family auth stamp to the current user's session-auth hash. Check active user/org, enrollment ownership/nonrevocation, family nonrevocation/absolute expiry, current submitter membership and channel scope. Do not replace the stale claim with a freshly loaded User and then compare that object to itself. Expiry/revocation/account/password/permission change yields 401 and clears online authority; a currently authenticated but unauthorized business action yields 403. Only successful current authorization issues or extends an offline lease.

POST refresh accepts exactly `{refresh_token}`. It is a bearer credential, not proof of possession; protected device custody, rotation and short access lifetime are required. Lock the same organization/user/enrollment/family order, then the refresh-credential row. Active unused credential and current family auth stamp yield one successor, mark predecessor consumed, and return a new pair. Family absolute expiry is unchanged. A consumed credential revokes its whole family and returns 401 `REFRESH_REUSED`; **commit family revocation before sending denial**, not inside a transaction that will roll back on a raised API exception. Invalid random token returns generic 401 `AUTH_REQUIRED` without revoking a guessed family. Audit/state transition failures return 503 and grant no new token. Preserve consumed credential digests for the family lifetime; M2 starts no purge job.

Lost refresh response: do not retry that refresh credential blindly. Pause, close protected content when online authority is uncertain, retain encrypted queue, and request online password-plus-proof REAUTHENTICATE into the same active enrollment. Query original pending receipts first, then retry exact frozen operations. Lost ordinary report responses use receipt/replay recovery and require no new operation ID. Client serializes refresh per enrollment and fences all late responses with an account-context generation; a response from an old generation cannot reopen storage or replace tokens after logout/switch/revocation.

Logout revokes the current family and returns `{logged_out:true}` after commit. Retrying with a now-revoked bearer receives 401, which the client treats as a locally completed logout, not restored authority. Local logout always cancels work, closes handles, clears sensitive memory and locks retained encrypted data even if offline/server unavailable. An offline logout cannot prove server revocation; the UI states that limitation and offers online reauthentication/revocation later. No token refresh or cached lease bypasses explicit logout.

## Frozen report request, canonical hash and receipt

OperationRequest has exactly `operation_id`, `report_id`, `expected_revision`, `template_version`, `payload`; Idempotency-Key equals the canonical lowercase operation UUID. The template is **`demo-maintenance-v1`**, not the shorthand `maintenance-v1`. Each payload field below is required, non-null and a string. Do not silently trim values; leading/trailing spaces and Unicode spelling are part of immutable content.

| Field | Validation |
|---|---|
| observed_at | At most 50 Unicode scalar values; timezone-aware ISO date-time accepted by current Django parse_datetime; at most five minutes ahead of server time; Android emits UTC RFC3339 with seconds and `Z` and then preserves it |
| category | `INFRASTRUCTURE`, `WATER_SUPPLY`, `EQUIPMENT` |
| urgency | `ROUTINE`, `PRIORITY` |
| area_label | `Area A`, `Area B`, `Area C` |
| site_label, reporter_label | Nonempty, at most 100 Unicode scalar values each |
| narrative | Nonempty, at most 2000 Unicode scalar values |
| assistance_requested | `Repair assistance`, `Inspection`, `Replacement parts` |

`expected_revision` is an integer (not bool, float or quoted number) in 0..2147483646; zero creates a report, positive corrects the current returned revision. Mobile UUIDs must be canonical lowercase strings, not accepted aliases. Mobile rejects lone surrogate code points and unknown fields before hashing. Browser historical acceptance stays unchanged; any shared validation strengthening needs explicit M1 regression evidence. Empty/unknown template returns 422 `TEMPLATE_UNSUPPORTED` on mobile; missing/null/wrong-type template remains ordinary 422 validation. No operation is reserved by a validation failure. Observed-time validity is checked on first acceptance and replay validation preserves the existing serializer rule; elapsed time does not make an old valid observation too old.

Canonical request bytes are **UTF-8 of Python-compatible JSON with sorted ASCII schema keys, no insignificant whitespace, `ensure_ascii=False`, no Unicode normalization, no escaped slash, literal non-ASCII scalar values, and JSON escapes for quote/backslash/control characters**. Control code points U+0000..U+001F use `\b`, `\f`, `\n`, `\r`, `\t` when applicable and lowercase `\u00xx` otherwise. Only the schema's bounded integers exist; floats/exponent numeric tokens are rejected. Hash envelope is `{"body":<request object>,"route":"POST /sync/operations/"}` with sorted keys. Digest is lowercase SHA-256 hex. The physical mobile prefix is deliberately **absent** from this historical logical route. Escaped-vs-literal JSON strings and reordered object members decode identically; `Z` vs `+00:00`, different whitespace inside a string, and NFC vs decomposed Unicode remain distinct strings and therefore hashes. See `contracts/fixtures/sync/mobile-canonical.json` and the executable fixture verifier. Freeze the exact outgoing JSON bytes locally together with its canonical envelope digest before enqueueing; retries send those stored bytes, not freshly serialized mutable fields.

Receipt is exactly the existing M1 acceptance shape:

```json
{"operation_id":"11111111-1111-4111-8111-111111111111","report_id":"22222222-2222-4222-8222-222222222222","revision_id":"33333333-3333-4333-8333-333333333333","revision_no":1,"delivery_status":"RECEIVED","processing_status":"PENDING","shared":false}
```

Its `processing_status` and `shared` describe historical acceptance and never change. Before acknowledging locally, validate exact operation/report IDs, canonical revision UUID, revision number `expected_revision+1`, `delivery_status=RECEIVED`, `processing_status=PENDING`, boolean `shared=false`; reject absent/wrong-type/mismatched fields and retain queue. Save receipt and mark RECEIVED in one local transaction guarded by account generation and claim token. A 2xx response alone is not an acknowledgement. Receipt metadata is private and never a publication.

Server acceptance commits immutable source revision, processing job, permanent accepting enrollment/operation/hash, receipt and audit together before 201. The namespace is `mobile:<stable enrollment UUID>`; refresh-family changes do not change it. Same namespace/operation/hash replay returns 200 original receipt, including reconstructed receipt from permanent revision identity where required. A changed hash returns 409 `IDEMPOTENCY_CONFLICT`. Different enrolled devices may use the same operation UUID independently. Existing browser origin remains accepting user with accepted_device NULL. Mobile receipt lookup never falls through to another device's or browser origin, even for the same owner. Current authorized own-report detail can show an historical receipt as part of that source's history; this does not make it discoverable by another origin's operation lookup.

Initial report UUID remains globally unique, including historical M1 data. The existing distinction between an unused versus an inaccessible existing UUID on attempted writes remains a documented low-severity inference limitation; this contract does not claim uniform write-existence hiding. Source/receipt reads use identical 404 for unknown or inaccessible IDs and expose no other author's records/counts. IDs are never adopted automatically after a conflict.

## Author status, correction and website revocation

GET reports accepts only M1 filters `status`, `date_from`, `date_to`, `page`, `page_size`, once each. Status values are ALL/PENDING/PROCESSING/AWAITING_REVIEW/FAILED/APPROVED/RETURNED/REJECTED, default ALL; page starts 1, max2147483647; page_size1..50, default10; dates are real UTC YYYY-MM-DD and start<=end. Return `{results,count,page,page_size,total_pages}` from the currently authorized author's reports, newest `(created_at,id)` first. Item fields are `id,reference,category,urgency,area_label,created_at,observed_date,revision_no,status,variant_id,feedback`, matching M1 `summary`; private feedback is escaped display-only text. No cached grant or total can widen scope.

GET revision returns `{report,payload,receipt,can_correct,history,workflow}` matching M1 revision view under an additional mobile submitter restriction; no recipient projection endpoint is added. `history` items are `{revision_no,received_at,status}`. `workflow` retains the bounded existing `revision_workflow` shape and its private allowlist; mobile may ignore it but must not persist arbitrary unvalidated fields. A current RETURN decision allows only the original author with live unit scope to create a new draft of that report with expected_revision=current revision and a new operation ID. Concurrent or stale corrections return 409 and preserve both local/server versions for explicit user choice. No automatic merge, mutation of an existing frozen row or approved-report editing.

Device list response is `{results:[{id,label,created_at,last_authenticated_at,revoked_at}],count}`; dates UTC RFC3339, revoked_at nullable; ordered newest `(created_at,id)` first. No key fingerprints/public keys, tokens/digests, installation UUIDs, other users, report counts or raw device identifiers. Every owner may view/revoke their own historical enrollments using their existing current web identity, even after a business-role change; enrollment/use remain submitter-only. Empty POST revoke is idempotent as a state transition: lock org/user/enrollment/families, verify ownership, set revoked_at once, revoke active families, record one first-transition audit, commit and return `{id,revoked:true,revoked_at}`. Repeat returns the original timestamp; unknown/other-owner IDs return the same 404. No Idempotency-Key ledger is claimed. Revoked enrollment never reactivates and retains its immutable history. This is separate from administrator account deactivation and confers no review authority.

## Local store, lifecycle and denial behavior

Separate account/enrollment stores hold current context+lease, editable Draft, immutable SubmittedSnapshot, OutboxOperation, committed Receipt and bounded own-report cache. Draft fields may be incomplete. Submit atomically validates/finalizes a snapshot and inserts its outbox row; exactly one operation ID and report ID are generated for that action. Freeze the authenticated user/org/enrollment/unit/channel/profile/template tuple with every submitted snapshot. Before draining, compare it to current verified context: same-enrollment reauthentication after a unit/channel/profile/template reassignment must pause with CONTEXT_CHANGED, never send an old-context queue as a new-context report. Permission-version changes always require current authorization even when the semantic tuple remains equal; equality is not an authorization grant. Client retains both contexts for explicit reconciliation without changing frozen bytes/IDs. Backend still derives current scope from locked authority and never trusts this local tuple as a permission. Local delivery state is QUEUED/SENDING/RECEIVED/NEEDS_CORRECTION/CONFLICT with a separate pause reason AUTH_REQUIRED/LOCKED/LEASE_EXPIRED/REVOKED/SCOPE_DENIED/CONTEXT_CHANGED. Preserve immutable rows in every pause/failure. New explicit correction creates a new row/operation and retains predecessor linkage.

Claim/drain uses short Room transactions, a random fencing token and persisted boot/session context; network I/O is outside transactions. Foreground and WorkManager share this routine, claim only their authenticated enrollment, and save a result only if generation/claim still matches. Reopen scans unacknowledged rows and repairs scheduling gaps. WorkManager input contains opaque account/row references only, never raw content/tokens. Retry RECEIVED is prohibited. Cache at most 100 own-report summaries and only an explicitly opened revision; clear private cache on scope denial, never the encrypted immutable pending queue.

SQLCipher encrypts Room, with random per-account keys wrapped by a separate Android Keystore AES key. No plaintext fallback, embedded key, destructive migration or empty-store replacement on wrong key. Capture Android `SystemClock.elapsedRealtime()` at **request start**; this monotonic clock includes deep sleep. Do not substitute `uptimeMillis()` or a timer whose elapsed duration pauses during sleep. Calculate the deadline as request_start plus the minimum of offline_lease_seconds, offline_lease_expires_at minus server_time, and family_expires_at minus server_time. Reject inconsistent response fields, nonpositive duration and any response whose arrival elapsedRealtime is **greater than or equal to** that deadline; response transit can shorten but never extend the lease. Every later lease check also expires at `now >= deadline`. Anchor this deadline to the same checked boot identity. Process restart may restore continuity with that boot marker; reboot/untrusted clock continuity requires online authorization before protected access. Wall-clock rollback never extends the lease. A local PIN/biometric proves device unlock only and cannot renew server authority. Login with a different account cannot open or drain an earlier queue.

The required wrapping-key policy on eligible API35+ devices is AES256/GCM/NoPadding, randomized encryption required, a fresh 12-byte IV for every wrap, user-authentication required, `setUserAuthenticationParameters(60, AUTH_DEVICE_CREDENTIAL | AUTH_BIOMETRIC_STRONG)` and **`setUnlockedDeviceRequired(true)`**. A secure device credential must exist. TASK-057 measured this exact policy on API36 through provision, locked denial, credential unlock, expiry after 65 seconds, reauthentication and denial after removal of the isolated emulator credential. Strong biometric authentication was not exercised. Authentication/key failure pauses storage access; no unbound-key or older-API fallback. The selected API35 floor follows [Android's documented unlocked-device fixes](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean)); it does not replace device verification. Device-unlocked state, recent credential/biometric authorization and server lease are separate mandatory checks. The P-256 proof key has its own per-account alias and cannot unwrap the database key or extend the offline lease.

On app/device lock, app background transition, logout, account switch, lease expiry or known server revocation: cancel matching work, invalidate generation, close all SQLCipher handles, clear decrypted keys/tokens/UI memory and require authorized unlock. Requiring auth to unwrap once does not lock an already-open database. A scheduled worker may acquire a new short-lived store context only after checking current account/generation, non-logout state, lease/boot continuity, device unlock and successful authenticated unwrap; an old foreground handle cannot be reused across a background fence. Close worker handles on completion/cancellation. Expired authorization leaves work paused for user unlock, rather than keeping passphrases alive to bypass the 60-second key policy. Before first unlock after reboot, do not open credential-protected stores or copy report work to direct-boot storage. Missing/invalidated keys retain encrypted files and expose recovery limitation; uninstall/data clearing/key loss do not have a promised recovery path. Disable/exclude database, WAL/SHM/journal, key envelopes, tokens and private caches from cloud/device-transfer backup; test the merged config and copied-file canaries.

401 stops protected reads/drain; one serialized refresh attempt is allowed only for an ordinary expired access token while the active account remains unlocked/within policy. Any invalid/revoked/uncertain refresh pauses until password-and-proof recovery. 403 locks current protected content for current-scope failure; 404 receipt keeps operation pending and permits exact replay after a current-authority check; 409 retains frozen data for explicit reconciliation; 422 preserves rejected operation as NEEDS_CORRECTION; 429/network/5xx preserve queue with bounded safe error code/backoff. A lost/malformed 2xx is uncertain acceptance, not rejection: receipt lookup first, then exact replay. OS force-stop may prevent background work until reopen; no uninterrupted background-service guarantee.

## Transactions and additive schema

All mobile protected reads/writes, refresh, reauthentication, web device revocation and account/grant changes use one order: Organization → affected Users sorted UUID → DeviceEnrollments sorted UUID → DeviceFamilies sorted UUID → challenge/refresh credential rows → Report → acceptance/revision/receipt rows. The existing coarse organization lock is deliberately retained. Authentication may parse/verify token outside locks but must carry original claims to revalidation in the business transaction. Password verification before lock is only preliminary: compare the captured credential stamp again under lock before issue. Account admin paths must follow the same organization/user order before revoking family rows. No arbitrary direct-admin update path may bypass service ordering.

Failed ordinary business writes roll back all effects; explicit security transitions (consume invalid proof, revoke a reused-refresh family) must instead commit their denial metadata/state before raising/returning the safe error. Implement a transaction result describing accepted/denied, not an exception that silently undoes required revocation. Preserve the current absence of database ATOMIC_REQUESTS; an outer request transaction must not undo a separately returned denial transition. Audit failure never yields successful authority or a successful report receipt. Test denial transitions by querying persisted rows after the 401 and concurrent replay, not only checking the response status.

## Exact error envelope and required negative fixtures

Errors are `{code,message}` with optional allowlisted schema `errors`; no raw request values. Only `ENROLLMENT_EXISTS` additionally permits one canonical UUID `enrollment_id`, and only after matching owner/password/proof/key/installation verification. No other error exposes that field. Auth failures on mobile are **401 with `WWW-Authenticate: Bearer realm="kapit-mobile"`**, including expired/invalid bearer and refresh/proof errors. Existing web authentication/CSRF failures retain their 403 behavior. Scope-specific mobile error handling must preserve the header; the current shared handler's unconditional auth 403 needs a narrow reviewed change, not global behavior replacement.
